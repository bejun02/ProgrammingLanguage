## 1. 프로젝트 개요

### 1.1 배경
(주)K반도체는 AI 반도체 시장 성장에 대응하여 파운드리 사업에 진출하였으며, 대형 고객사 주문에 맞춰 기존 메모리 반도체 팹을 파운드리 제조 팹으로 리뉴얼하고 있습니다. 본 프로젝트는 세계 최고 수준의 스마트 팹(Smart Fab) 구현을 위한 **공정 최적화 시뮬레이션**입니다.

### 1.2 목표
| 목표 | 설명 |
|------|------|
| **생산량 최대화** | 주어진 기간(15일) 내 제품 생산량(Throughput) 극대화 |
| **비용 최소화** | 동일 생산량 조건에서 설비 및 AMR 투자 최소화 |
| **Profit 최대화** | 매출 대비 비용 효율성 극대화 |

### 1.3 Profit 계산 공식
```
Profit = [100 × min(A완성품, B완성품) - 5 × 총출고수] / [설비비용 + AMR비용] × 100,000
```

### 1.4 제약 조건
| 항목 | 제약 |
|------|------|
| 시뮬레이션 시간 | 15일 = **1,296,000초** |
| 최대 설비 수 | **30대** 이내 |
| 최대 AMR 수 | **30대** 이내 |
| 설비 위치 | 30개 고정 좌표 중 선택 |
| 공정 순서 | A(산화) → B(노광) → C(식각) → D(증착) → E(계측) |
| 사이클 | **2회 반복** 후 완성 |

### 1.5 공정별 소요 시간 (분)
| 제품 | A1 | B1 | C1 | D1 | E1 | A2 | B2 | C2 | D2 | E2 |
|------|----|----|----|----|----|----|----|----|----|----|
| **ProdA** | 15 | 15 | 15 | 15 | 15 | 15 | 15 | 15 | 15 | 15 |
| **ProdB** | 5 | **40** | 25 | 2 | 5 | 10 | 10 | 5 | 10 | 15 |

> **병목 공정**: ProdB의 B1(40분)이 가장 길며, C와 E 공정이 전체 병목

## 2. 시스템 구조

### 2.1 이산 사건 시뮬레이션 (Discrete Event Simulation)
본 프로젝트는 **이산 사건 시뮬레이션(DES)** 방식으로 구현되었습니다.

```
┌─────────────────────────────────────────────────────────────────┐
│                    이벤트 루프 (Event Loop)                      │
├─────────────────────────────────────────────────────────────────┤
│  1. schedule(time, callback) → 이벤트 예약 (heapq 우선순위 큐)   │
│  2. run() → 시간순으로 이벤트 처리                               │
│  3. 이벤트 실행 중 새로운 이벤트 schedule 가능                   │
└─────────────────────────────────────────────────────────────────┘
```

- **heapq 기반 우선순위 큐**: 이벤트를 시간순으로 정렬하여 가장 이른 이벤트부터 처리
- **연쇄 이벤트**: 하나의 이벤트 처리 중 새로운 이벤트가 예약될 수 있음
- **종료 조건**: SIM_END(1,296,000초) 도달 또는 이벤트 큐가 비어있음

## 3. 과업별 개선 내용

### 과업 1: AMR 이동/라우팅 개선

#### 3.1.1 과제 조건
과제 설명에 따르면 **AMR 간 충돌은 고려하지 않습니다.** 따라서 본 개선안에서는 AMR 간 충돌이 아닌, **설비 금지 구역**만을 고려하여 AMR 이동 경로를 최적화합니다.

#### 3.1.2 문제점 (기존 방식)
- **유클리드 직선거리** 기반 이동 시간 계산
- 설비가 배치된 공간을 직선으로 통과하는 비현실적 거리 계산
- Warehouse → 각 설비 → Stocker 간의 **실제 이동 가능한 최단 거리**를 반영하지 못함

#### 3.1.3 개선 방안: 설비 금지 구역 설정 및 다익스트라 알고리즘 적용

**1단계: 설비 금지 구역 (Obstacle Zone) 정의**

설비 크기가 3m × 2m이므로, 설비 중심 좌표를 기준으로 금지 구역을 설정합니다.

```python
class ObstacleZone:
    """
    설비 중심 좌표로 금지 구역 생성
    설비 크기: 3m × 2m → 중심 기준 좌우 1.5m, 상하 1.0m
    
    예: 중심 (14, 3) → 금지구역
        x: 12.5 ~ 15.5
        y: 2.0 ~ 4.0
    """
    def __init__(self, center_x: float, center_y: float):
        self.x_min = center_x - 1.5  # 좌측 경계
        self.x_max = center_x + 1.5  # 우측 경계
        self.y_min = center_y - 1.0  # 하단 경계
        self.y_max = center_y + 1.0  # 상단 경계
```

**2단계: 그래프 노드 구성**

AMR이 이동할 수 있는 지점들을 노드로 설정합니다.

| 노드 종류 | 좌표 계산 | 설명 |
|----------|----------|------|
| Warehouse | (4, 10) | 원자재 창고 고정 위치 |
| Stocker | (56, 10) | 완제품 보관소 고정 위치 |
| 설비 입력포트 | (center_x - 2, center_y) | 설비 좌측 2m 지점 |
| 설비 출력포트 | (center_x + 2, center_y) | 설비 우측 2m 지점 |

**3단계: 다익스트라 최단 경로 탐색**

금지 구역을 우회하는 최단 경로를 계산합니다.

```python
def dijkstra(start, end):
    """
    다익스트라 알고리즘으로 최단 경로 탐색
    
    알고리즘:
    1. 시작 노드에서 모든 노드까지의 거리를 무한대로 초기화
    2. 우선순위 큐에 시작 노드 추가 (거리 0)
    3. 큐에서 가장 가까운 노드 추출
    4. 해당 노드에서 이동 가능한 모든 노드로의 거리 갱신
       - 단, 두 노드 간 직선이 금지 구역과 교차하면 이동 불가
    5. 목적지 도달 시 경로 반환
    """
    # 직선 이동 가능 여부 확인
    if can_move_direct(start, end):
        return euclidean_dist(start, end), [start, end]
    
    # heapq 기반 우선순위 큐로 최단 경로 탐색
    pq = [(0.0, start)]
    dist_map = {start: 0.0}
    parent = {start: None}
    
    while pq:
        curr_dist, curr = heapq.heappop(pq)
        if curr == end:
            return curr_dist, reconstruct_path(parent, end)
        
        for next_node in all_nodes:
            if can_move_direct(curr, next_node):
                new_dist = curr_dist + euclidean_dist(curr, next_node)
                if new_dist < dist_map.get(next_node, inf):
                    dist_map[next_node] = new_dist
                    parent[next_node] = curr
                    heapq.heappush(pq, (new_dist, next_node))
    
    return euclidean_dist(start, end), [start, end]  # fallback
```

**4단계: 경로 캐싱으로 성능 최적화**

동일한 출발점-도착점 쿼리가 반복될 수 있으므로, 결과를 캐싱하여 재계산을 방지합니다.

```python
ENABLE_PATH_CACHE = True
_path_cache: Dict[Tuple, Tuple[float, List]] = {}

def pathfinding_dist(a, b) -> float:
    """캐싱을 적용한 경로 거리 계산"""
    cache_key = (a, b)
    if ENABLE_PATH_CACHE and cache_key in _path_cache:
        return _path_cache[cache_key][0]
    
    distance, path = path_graph.dijkstra(a, b)
    
    if ENABLE_PATH_CACHE:
        _path_cache[cache_key] = (distance, path)
    
    return distance
```

#### 3.1.4 적용 결과

| 구간 | 유클리드 거리 | 다익스트라 거리 | 비고 |
|------|--------------|----------------|------|
| WH → A-1 입력포트 | 12.2m | 12.2m | 직선 가능 (장애물 없음) |
| A-1 출력 → B-1 입력 | 8.0m | 8.0m | 직선 가능 (장애물 없음) |
| B-1 출력 → C-1 입력 | 8.0m | 10.3m | 설비 우회 필요 |
| E-1 출력 → STK | 12.2m | 12.2m | 직선 가능 (장애물 없음) |

- **직선 이동 가능 시**: 유클리드 거리 = 다익스트라 거리 (금지 구역과 교차하지 않음)
- **우회 필요 시**: 다익스트라 거리 > 유클리드 거리 (금지 구역을 피해 경유)
- **성능**: 경로 캐싱으로 반복 쿼리 시 O(1) 조회

```python
# 기존 라운드로빈 방식
rr = global_variable.ROUND_ROBIN_IDX.get(stage, 0)
```

**문제점:**
1. 설비의 **현재 부하 상태**를 고려하지 않음
2. **이동 거리**(AMR 이동 시간)를 고려하지 않음
3. **병목 공정**에 대한 우선순위가 없음
4. **1차/2차 사이클 비율**을 맞추지 못함

#### 3.2.4 개선 방안: Score 기반 휴리스틱 알고리즘

**휴리스틱을 사용한 이유:**

반도체 공장의 디스패칭 문제는 **NP-hard** 문제로, 최적해를 구하는 것이 현실적으로 불가능합니다. 따라서 **휴리스틱(경험적 규칙)**을 사용하여 "충분히 좋은" 해를 빠르게 찾습니다.

본 프로젝트에서는 여러 요소를 종합한 **Score 함수**를 정의하고, Score가 최소인 설비를 선택합니다.

**Score 공식:**

```
Score(m) = LocalWait(m) + α×DownstreamWork(m) + β×MoveTime(m) + Δ(t,p) + BN(t)
```

**각 요소의 의미와 계산 방법:**

| 요소 | 공식 | 설명 | 목적 |
|------|------|------|------|
| **LocalWait(m)** | `max(avail_time[m], now + move_time) - now + process_time` | 해당 설비에서 작업 완료까지 예상 시간 | 빨리 끝나는 설비 선호 |
| **DownstreamWork(m)** | `Σ(대기 Job들의 R_sys) / scale` | 설비 큐에 대기 중인 작업의 남은 공정 시간 합 | 큐가 짧은 설비 선호 |
| **MoveTime(m)** | `pathfinding_dist(현재위치, 설비) / AMR속도` | AMR 이동 시간 (다익스트라 거리 사용) | 가까운 설비 선호 |
| **Δ(t,p)** | `±γ × (target_ratio - current_ratio)` | 1차/2차 사이클 비율 보정 | A:B 균형 유지 |
| **BN(t)** | `-δ (if 병목 공정)` | 병목 공정에 대한 보너스 | 병목 공정 우선 처리 |

**알고리즘 상세 설명:**

**1. LocalWait(m) - 지역 대기 시간**

```python
# avail_time[m]: 설비 m이 현재 작업을 마치고 비게 되는 시각
# move_time: 현재 위치에서 설비 m까지 AMR 이동 시간
# process_time: 해당 공정의 처리 시간

avail_time = heuristic_state.avail_time.get(m.name, now)
move_time = pathfinding_dist(current_pos, m.input_port) / AMR_SPEED
local_wait = max(avail_time, now + move_time) - now + process_time
```

- 설비가 이미 비어있으면(`avail_time < now + move_time`): AMR 도착 후 바로 시작
- 설비가 아직 작업 중이면(`avail_time > now + move_time`): 설비가 빌 때까지 대기 후 시작

**2. DownstreamWork(m) - 하류 작업량**

```python

    r_sys = calculate_remaining_time(
        queued_job.product,      # ProdA 또는 ProdB
        queued_job.cycle_idx,    # 현재 사이클 (0 또는 1)
        target_stage,            # 다음 공정
```

- **효과**: 큐가 긴 설비를 피하여 부하 분산

**3. Δ(t,p) - 1차/2차 비율 보정**

```python
# target_ratio: 목표 1차 비율 (공정별로 다름)
```

### 과업 3: 제품 투입 시기 동적 조정

#### 3.3.1 문제점 (기존 방식)
- ProdA, ProdB **단순 순차 생성**: A → B → A → B → ...
- 라인 상태와 무관하게 무조건 투입
- **라인 불균형** 발생: 특정 공정에 WIP(재공품)가 과도하게 쌓임
- 재가공품(2차 사이클)이 신규품에 밀려 완성이 지연됨

#### 3.3.2 개선 방안 1: Pull 방식 제품 이동

**Push vs Pull 방식 비교:**

| 방식 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **Push** | 이전 공정이 완료되면 다음 공정으로 밀어넣음 | 단순 | 병목 앞에 WIP 축적 |
| **Pull** | 다음 공정이 빈 슬롯이 생기면 이전 공정에서 당겨옴 | 부하 분산 | 구현 복잡 |

본 프로젝트에서는 **Pull 방식**을 채택하여 설비 유휴 시간을 최소화합니다.

```python
def pull_from_prev_to(m_next: Machine, policy: str = "eta"):
    """
    다음 설비(m_next)의 입력 슬롯이 열렸을 때,
    이전 공정 설비들 중에서 제품을 당겨오는 Pull 방식
    
    동작 원리:
    1. m_next의 입력 슬롯이 비었음을 감지
    2. 이전 공정(prev_stage)의 모든 설비 검색
    3. output_buf에 제품이 있고, 예약/이송 중이 아닌 것 필터링
    4. 정책(policy)에 따라 최적의 소스 선택
    5. AMR 예약 후 이동 스케줄 등록
    
    정책(policy) 옵션:
    - 'eta': AMR 도착 예정 시간(ETA) 최소화 (기본)
    - 'cyclemax': cycle_idx가 높은 제품(재가공품) 우선
    - 'wipbal': WIP가 많은 설비에서 우선 추출 (라인 밸런싱)
    - 'nearby': 거리가 가까운 설비 우선
    - 'oldest': job_id가 작은(오래된) 제품 우선
    """
    nxt = m_next.stage
    prev_stages = PREV_OF.get(nxt, [])  # 예: B의 이전은 A
    prev_machines = []
    
    for p in prev_stages:
        if p == "WH":
            continue  # Warehouse는 별도 처리
        prev_machines.extend(global_variable.MACHINES.get(p, []))
    
    # 입력 슬롯 예약 (경합 방지)
    if not reserve_input(m_next):
        return
    
    # 최적의 소스 설비 선택
    drop_xy = m_next.input_port
    pick = select_upstream_source(prev_machines, drop_xy, policy=policy)
    
    if pick is None:
        release_input(m_next)
        return
    
    src_m, job = pick
    # AMR 예약 및 이동 스케줄 등록...
```

**select_upstream_source() 함수:**

```python
def select_upstream_source(prev_machines, drop_xy, policy="eta"):
    """
    이전 공정 설비들 중 제품을 당겨올 최적의 소스 선택
    
    후보 조건:
    - output_buf에 job이 있음
    - reserved = False (아직 예약되지 않음)
    - in_transit = False (이송 중이 아님)
    """
    cands = []
    
    for m in prev_machines:
        job = m.output_buf
        if job is None or job.reserved or job.in_transit:
            continue
        
        pick_xy = m.output_port
        
        # 정책별 점수 계산
        if policy == "eta":
            # AMR ETA가 가장 빠른 소스 선택
            load_sec = load_time_for(m.stage)
            unload_sec = unload_time_for(next_stage_for(job, m.stage) or "STK")
            score = _predict_eta_for_pick(
                global_variable.AMRS, None, pick_xy, drop_xy,
                load_sec, unload_sec, global_variable.now
            )
        elif policy == "cyclemax":
            # 재가공품(cycle_idx=1) 우선 (음수로 정렬)
            score = -job.cycle_idx
        elif policy == "wipbal":
            # WIP가 많은 설비에서 먼저 빼줌 (라인 밸런싱)
            wip = len(m.input_buf) + (1 if m.processing_job else 0)
            score = -wip
        elif policy == "nearby":
            score = pathfinding_dist(pick_xy, drop_xy)
        elif policy == "oldest":
            score = int(job.job_id.split("-")[-1])
        
        cands.append((score, m, job))
    
    if not cands:
        return None
    
    cands.sort(key=lambda x: x[0])
    return cands[0][1], cands[0][2]  # (설비, job)
```

#### 3.3.3 개선 방안 2: 재가공품 우선 투입

**재가공품 우선 처리의 필요성:**

| 제품 상태 | 남은 공정 수 | 완성까지 시간 |
|----------|-------------|--------------|
| 신규품 (cycle=0, stage=A) | 10개 공정 | 길다 |
| 재가공품 (cycle=1, stage=A) | 5개 공정 | 짧다 |

재가공품은 이미 1차 사이클(A→B→C→D→E)을 완료한 상태이므로, 2차 사이클만 거치면 완성됩니다. 따라서 **재가공품을 우선 처리**하면 완성품 수가 빨리 늘어납니다.

```python
def _exists_priority_job_for_A() -> bool:
    """
    E→A 재가공품이 존재하는지 확인
    
    조건:
    1. E공정 설비의 output_buf에 제품이 있음
    2. 해당 제품이 예약되지 않았고 이송 중도 아님
    3. 다음 스테이지가 A (재순환)
    4. cycle_idx >= 1 (2차 사이클 진입)
    
    사용처:
    - try_dispatch_from_warehouse_to_A()에서 호출
    - True이면 창고→A 신규 투입을 보류하고 E→A 재가공품 먼저 처리
    """
    for m in global_variable.MACHINES.get("E", []):
        j = m.output_buf
        if j and (not j.reserved) and (not j.in_transit):
            nxt = next_stage_for(j, m.stage)
            if nxt == "A" and getattr(j, "cycle_idx", 0) >= 1:
                return True
    return False
```

#### 3.3.4 개선 방안 3: pending_stage 캐싱으로 중복 계산 방지

**문제 상황:**

`next_stage_for()` 함수는 Job의 다음 스테이지를 결정합니다. 이 함수가 여러 번 호출되면 `cycle_idx`가 중복으로 증가하는 **버그**가 발생할 수 있습니다.

```python
# 버그 있는 코드 (매 호출마다 cycle_idx 증가 가능)
def next_stage_for_buggy(job, current_stage):
    i = ROUTE.index(current_stage)
    if i + 1 < len(ROUTE):
        return ROUTE[i + 1]
    
    # E 완료 → 사이클 체크
    if job.cycle_idx + 1 < job.max_cycles:
        job.cycle_idx += 1  # ★ 버그: 여러 번 호출되면 중복 증가!
        return ROUTE[0]
    return None
```

**해결: pending_stage 캐싱**

```python
def next_stage_for(job: Job, current_stage: str) -> Optional[str]:
    """
    현재 공정 완료 후 다음 스테이지 결정
    
    중요: pending_stage가 이미 설정되어 있으면 그대로 반환
    이 체크가 없으면 next_stage_for()가 여러 번 호출될 때
    cycle_idx가 중복 증가하는 버그 발생!
    """
    # ★ 핵심: 이미 계산된 다음 스테이지가 있으면 바로 반환
    if getattr(job, "pending_stage", None):
        return job.pending_stage
    
    try:
        i = global_variable.ROUTE.index(current_stage)
    except ValueError:
        return None
    
    # 아직 E가 아니면 다음 공정으로
    if i + 1 < len(global_variable.ROUTE):
        job.pending_stage = global_variable.ROUTE[i + 1]  # 캐싱
        return job.pending_stage
    
    # E 완료 → 사이클 반복 여부 확인
    if job.cycle_idx + 1 < job.max_cycles:
        job.cycle_idx += 1
        job.pending_stage = global_variable.ROUTE[0]  # A로 돌아감, 캐싱
        return job.pending_stage
    
    return None  # 2사이클 완료 → Stocker로
```

## 5. 핵심 알고리즘 상세

### 5.1 AMR 예약 알고리즘
```python
def reserve_amr(pick_xy, drop_xy, request_time, load_sec, unload_sec):
    """
    AMR 예약 - ETA 최소화 기준 선택
    
    타임라인 계산 (pathfinding 적용):
    ┌─────────────────────────────────────────────────────────────┐
    │ depart_at = max(request_time, amr.free_time)                │
    │ arrive_pick = depart_at + dist(현재위치, 픽업) / 속도       │
    │ depart_pick = arrive_pick + load_sec (10초)                 │
    │ arrive_drop = depart_pick + dist(픽업, 드롭) / 속도         │
    │ depart_drop = arrive_drop + unload_sec (10초)               │
    └─────────────────────────────────────────────────────────────┘
    
    dist() 함수는 pathfinding_dist() 사용 (설비 우회)
    """
```

### 5.2 설비 가공 시작 로직
```python
def try_start_processing(m: Machine):
    """
    설비 가공 시작 시도
    
    1. input_buf가 비어있으면:
       - A공정: pull_from_prev_to(policy="cyclemax") → 재가공품 우선
       - 다른 공정: pull_from_prev_to(policy="eta")
    
    2. waiting_done에 제품 있으면: 대기 (output_buf 비워질 때까지)
    
    3. input_buf에서 cycle_idx 가장 큰 제품 선택 (재가공 우선)
       → 완성까지 남은 공정이 적어 효율적
    """
```

### 5.3 다음 공정 이동 로직
```python
def move_to_next_stage_from_output(m: Machine):
    """
    output_buf → 다음 공정 이동
    
    Case 1: nxt = None (2사이클 완료)
        → Stocker로 출하
    
    Case 2: nxt = "A" (재순환)
        → A공정 설비 선택 (휴리스틱)
    
    Case 3: 그 외 (B, C, D, E)
        → 다음 공정 설비 선택 (휴리스틱)
    
    설비 선택 후:
    1. reserve_input(drop_m) → 슬롯 선점
    2. reserve_amr() → AMR 예약
    3. schedule() → 이벤트 체인 등록
    """
```
